Request

Request: DATA-7391
Requested by: Help desk
Data: My book database, then your own database

Background

Users have started reporting that some searches are slow. Your manager wants you to learn how to find and fix slow queries by practising on a sample database, then check your own queries and write up a fix so the team can approve it. On a real system with millions of rows, a missing index can turn a search that takes seconds into one that takes minutes.

Learning Outcomes

By the end of this lab, you will be able to:

  • Read a query plan, and explain how an index changes it
  • Write commands that add an index to a table for a specific query
  • Optimize your own SQL queries, and decide whether an index is worth it
  • Write up a performance fix with evidence, the way you would for a work ticket

Lab Instructions

Parts 3 and 4 use your own data set and the queries you documented in the SQL Review labs. If you want to switch to a different data set, email me first. Switching means redoing the work from earlier labs for your new data set, so it adds a lot of work. The switching checklist (linked under Resources) lists what you'd need to redo.

Screenshots

Several parts of this lab ask for a screenshot. Each screenshot should have your name, term, and year. One of the easiest ways to do that is make a text document with your name and term/year on your computer and save it to use all term. Any screenshots that don't include this information won't be counted.

Part 1: Writing Efficient Queries on Kaggle

Sign up for Kaggle (linked under Resources). It's free, and you can use any email you want. You only need the Writing Efficient Queries lesson from Kaggle's Advanced SQL course, not the whole course.

  1. Read the Writing Efficient Queries tutorial.
  2. Do the Writing Efficient Queries exercise. It has problems about Pet Costumes International. Take a screenshot of your solution to both problems.
  3. In a few sentences, explain one technique from the tutorial that makes a query more efficient, and why it helps.

Kaggle uses BigQuery, which doesn't use indexes the way most databases do, so this part is about writing efficient queries. Parts 2 and 3 are about indexes.

Optional, not required for this class: if you're interested, the rest of Kaggle's Advanced SQL course covers joins and unions, analytic functions, and nested data.

Part 2: Indexes and Query Plans

Load my book database (linked under Resources) into any SQLite tool. I suggest SandboxSQL, linked under Resources: use Load a Database, then load the .sqlite file. Queries don't always copy over well from a PDF, especially single quotes, so type them in if you get an error.

How to read a query plan: put EXPLAIN QUERY PLAN in front of any query, and the database tells you how it will find the rows, without running the query. Look for these two words:

  • SCAN means the database reads every row in the table. On a big table, this is slow.
  • SEARCH ... USING INDEX means the database uses an index to go straight to the rows it needs.

The exact wording can be a little different depending on your tool, but SCAN and SEARCH will be there.

Worked example: this query finds books by one publisher.

EXPLAIN QUERY PLAN
SELECT title, publishDate FROM books
WHERE publisher = 'Penguin Books';

Before an index, the plan says SCAN books. Then I create an index on the column in the WHERE:

CREATE INDEX idx_books_publisher ON books(publisher);

Running the same EXPLAIN QUERY PLAN again now says SEARCH books USING INDEX idx_books_publisher. Follow the same steps for the questions below.

  1. This query finds the author and genre of a book with a given title. 
    SELECT authors.name, books.genre
FROM books INNER JOIN authors
ON books.author_id = authors.author_id
WHERE books.title = 'Dune';
    1. Run EXPLAIN QUERY PLAN on it, and take a screenshot of the plan.
    2. Write and run the command that creates an index to make this query more efficient.
    3. Run EXPLAIN QUERY PLAN again, and take a screenshot. Explain what changed in the plan and why that makes the query faster.
  2. Create an index on the genre column. Then write a query that shows only Fantasy books, with the author's name and the title. Run EXPLAIN QUERY PLAN on your query and take a screenshot that shows your index being used. If your plan still says SCAN books, check that your WHERE uses = with the indexed column. A LIKE that starts with % can't use an index.
  3. Indexes aren't free. They take up space, and they make adding or changing rows slower. Pick a column in your own data set that would be a bad choice for an index, and explain why. For example, think about columns that are rarely searched, have only a few different values, or change often.

Part 3: Optimize Your Own Queries

Pick 2 of your documented queries from the SQL Review labs. For each one:

  1. Run EXPLAIN QUERY PLAN on it, and take a screenshot.
  2. Decide whether an index would help. If it would, create it, run EXPLAIN QUERY PLAN again, and take a screenshot.
  3. Update the Notes in your query documentation with what the plan showed, any index you created, and whether it was worth it.

Your data set may be small, so you probably won't see a difference in time. The plan is your evidence. If you decide an index isn't worth it, that's a fine answer, as long as you explain why.

Part 4: Performance Ticket Write-Up

A user reports that one of your queries from Part 3 is slow. Write up the fix for your team lead, following the sample performance ticket (linked under Resources). Include the problem, the query, what you checked, what you changed, your evidence, the trade-offs, how to undo the change, and your recommendation.

Acceptance Criteria

This request is done when:

  • Both problems in the Kaggle Writing Efficient Queries exercise are solved, and you've explained one technique from the tutorial
  • Every index you create has a query plan from before and after as evidence
  • Your genre query plan shows your index being used
  • 2 of your own queries are checked, with an explanation of whether an index is worth it
  • Your performance ticket write-up includes everything in the sample, including how to undo the change
  • Every screenshot follows the screenshot rules

Deliverables

One file that includes:

  • Part 1: your 2 Kaggle screenshots and your explanation of one technique
  • Part 2: your answers, commands, queries, and plan screenshots
  • Part 3: your 2 updated query documentations with plan screenshots
  • Part 4: your performance ticket write-up
  • If you switched data sets: the redone work from the switching checklist

Audience: your team lead, who has to approve the change.
